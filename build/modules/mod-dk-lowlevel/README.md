# mod-dk-lowlevel

TRUE level-1 Death Knights. Artefacts **A15/A16/A17** of the feature design — see
`docs/death-knights.md` in this repo for the committed version, and `.work/notes/DESIGN.md` for the
full working document if you still have the scratch tree (`.work/` is gitignored). This file covers
only the module.

The module is a small part of the feature. Most of it is data: world-DB `*_dbc` override rows, a
handful of `playercreateinfo*` edits, and a client patch MPQ that supplies the tooltip. The module
exists to do the two things data cannot: hand out ranks the character has grown into, and stop
Acherus from wiping their talents.

## Why this module lives in the repo instead of on GitHub

Every other module on this realm is a pin in `build/modules.txt` that `build/Dockerfile` clones by
`owner/name ref sha`. This one has no upstream, and publishing a repo just to clone it back would
add a network dependency and a second place to look.

The Docker build context is `./build` (`.github/workflows/build.yml`: `context: ./build`), so a
module at the repo root would not be in the context at all. Putting it at `build/modules/` plus a
single `COPY modules/ /src/modules/` in the Dockerfile — placed **after** the clone loop, so the
local tree joins the eighteen cloned ones rather than being overwritten by them — keeps it here,
inside the workflow's existing `paths: ['build/**']` filter, and out of `build/.dockerignore`.

## Layout

```
build/modules/mod-dk-lowlevel/
  conf/mod_dk_lowlevel.conf.dist   REQUIRED — see below
  src/dk_lowlevel.h                hook declarations, config struct, generated-table asserts
  src/dk_lowlevel.cpp              Reconcile(), the three hooks, AddSC_dk_lowlevel()
  src/dk_lowlevel_loader.cpp       Addmod_dk_lowlevelScripts()
  src/dk_progression.h             GENERATED by tools/dkspells.py — DO NOT HAND-EDIT
  tools/dkspells.py                the one generator (spell_dbc SQL + client DBC + the header)
  data/sql/db-world/base/*.sql     module migrations, picked up by UpdateFetcher
```

**There is no `CMakeLists.txt`, and adding one would do nothing.** Not one of the eighteen
installed modules ships one. The core's `modules/CMakeLists.txt` never calls `add_subdirectory` on
a module; it enumerates `modules/*` that contain a `src/` directory (`ConfigureModules.cmake`
`GetModuleSourceList`) and then globs that `src/` with `CollectSourceFiles`, which recurses and
picks up `*.cpp`/`*.h`. `CollectIncludeDirectories` on the same path is what puts `src/` on the
include path, which is how `#include "dk_progression.h"` resolves. The only per-module CMake hook
that exists is an optional `modules/<name>/<name>.cmake`, and this module needs no extra
dependencies, so it does not have one either.

`conf/mod_dk_lowlevel.conf.dist` **is** required, and its absence fails silently. The compile-time
`CONFIG_FILE_LIST` is built from `file(GLOB ${MODULE_CONFIG_PATH}/*.conf.dist)`; a module with no
`.conf.dist` is never added to that list, so `ConfigMgr::LoadModulesConfigs` never opens its
`.conf` and every key falls back to its compiled-in default.

`data/` needs the local `.gitignore` in this directory. Read the comment in it before deleting it.

## The generated header is a hard build dependency

`src/dk_progression.h` is emitted by `tools/dkspells.py`, from the same spec that emits the
`spell_dbc` SQL and the patched client `Spell.dbc`. That is the whole point: one source, three
outputs, so the C++ table, the server's damage roll and the client's tooltip cannot drift (the
failure mode being a tooltip that says 10-12 while the server rolls 127-137).

The contract `dk_lowlevel.h` compiles against:

```cpp
#ifndef DK_PROGRESSION_H_          // any include guard; the header is included once
#define DK_PROGRESSION_H_

struct DkGrant
{
    uint8  level;
    uint32 spellId;
};

static constexpr DkGrant kDkProgression[] =
{
    { 1, 90000 },                  // ascending by level, no zero levels, no zero spell IDs
};

#endif
```

`dk_lowlevel.h` `static_assert`s that the table is non-empty, sorted ascending by level, and free
of zero levels and zero spell IDs. Sortedness is not cosmetic — `Reconcile` early-outs with
`break` on the first entry above the player's level, so an unsorted table would hand out a partial
spellbook that looks entirely plausible. Making it a compile error is cheaper than noticing it in
game.

**Consequence for the build order.** `DESIGN.md` 1.2 rebuilds the image at step 3 and runs the
generator at step 4. The module will not compile without the header, so the generator has to have
been run at least once — for the header alone if nothing else — before that first image build.

## The three hooks

Opted into explicitly. `PlayerScript`'s constructor treats an empty `enabledHooks` vector as "all
hooks" (`PlayerScript.cpp:963-971`), which would register this script against every dispatch list
in the core for the sake of three.

| hook | fork signature | why this one |
|---|---|---|
| `PLAYERHOOK_ON_LOGIN` | `void OnPlayerLogin(Player*)` — `PlayerScript.h:337` | Fires at `CharacterHandler.cpp:1131`, after `AddPlayerToMap` and after `m_playerLoading = false`, so `learnSpell`'s `if (IsInWorld()) SendLearnPacket(...)` reaches the client. Also fires *before* `OnPlayerFirstLogin`, so first login needs no separate hook. This is the only thing that catches an **offline** `.character level`, which writes raw SQL with no hook at all (`cs_character.cpp:1119-1126`). |
| `PLAYERHOOK_ON_LEVEL_CHANGED` | `void OnPlayerLevelChanged(Player*, uint8 /*oldlevel*/)` — `PlayerScript.h:267` | Fires at `Player.cpp:2583`, after `SetLevel` at `:2521`, so `GetLevel()` is already the new level and the argument is the old one. |
| `PLAYERHOOK_ON_CALCULATE_TALENTS_POINTS` | `void OnPlayerCalculateTalentsPoints(Player const*, uint32&)` — `PlayerScript.h:237` | Fires at `Player.cpp:13957`, inside `CalculateTalentsPoints`, before the `RATE_TALENT` multiply. Closes the Acherus wipe. |

> **Every `PlayerScript` virtual on this fork is `OnPlayerXxx`.** `OnLogin`, `OnLevelChanged` and
> `OnCreate` — the names in every AzerothCore tutorial — do not exist here. Writing one compiles
> perfectly: you have declared a new non-virtual member, and the hook never fires. `override` on
> all three is the guard, and it is the reason the table above cites line numbers.
>
> The renaming is `PlayerScript`-only. `WorldScript::OnAfterConfigLoad(bool)` (`WorldScript.h:53`)
> kept its original name.

Hooks deliberately **not** used: `OnPlayerCreate` (runs at `CharacterHandler.cpp:598` after
`SaveToDB`, on a `shared_ptr` destroyed immediately — nothing written there persists);
`OnPlayerLoadFromDB` (`PlayerStorage.cpp:5504`, before `_LoadSkills`/`_LoadSpells` — the spell map
is empty); `OnPlayerMapChanged` (`PLAYERHOOK_ON_MAP_CHANGED` is inert on this fork anyway — it is
dispatched with `ExecuteScript<PlayerScript>` instead of `CALL_ENABLED_HOOKS`, so the enabled-hooks
vector is ignored).

## Reconcile

```
if not DKLowLevel.Enable          -> return
if player->getClass() != 6        -> return
for each { level, spellId } in kDkProgression, ascending:
      if level > player level     -> break
      if not HasSpell(spellId)    -> learnSpell(spellId)
then the four ex-starter-chain utilities, each behind its own level gate and HasSpell guard:
      Death Gate 50977, Runeforging 53428, Apprentice Riding 33388 @20, Journeyman 33391 @40
```

**Idempotent.** The only mutation is `learnSpell`, guarded by `HasSpell` here and early-returning
on `HasActiveSpell` internally (`Player.cpp:3411-3416`). The effect is a pure function of
`(level, current spellbook)`; running it a thousand times equals running it once. `HasSpell`
(`Player.cpp:4039`) is true for a known-but-inactive spell, which is what we want: a rank
superseded by a higher one is still owned and must not be re-learned. Re-granting a low rank while
a higher one is active would be safe anyway — `addSpell` walks the chain, deactivates the lower
rank and sends `SMSG_SUPERCEDED_SPELL`, exactly as stock does today for Blood Strike on every
level-80 DK login — but it would be pointless churn.

**Correct in both directions.** Levelling up, online or offline, converges on the next hook or the
next login. Levelling down is a no-op: this function never revokes. That is deliberate, not an
omission. The core does not revoke on de-level either, and `Player::removeSpell` removes higher
ranks *recursively*, so a revoke pass would turn a GM typo into a destroyed spellbook. Levelling
back up re-enters the loop and finds everything already owned.

**`getClass()`, never `IsClass()`.** `Player::IsClass` (`Player.cpp:1348-1355`) asks
`sScriptMgr->OnPlayerIsClass()` first and returns whatever a module answers, so a third-party
module could make the check silently wrong in either direction — skipping real Death Knights, or
firing for non-Death-Knights. `Unit::getClass()` (`Unit.h:844`) reads `UNIT_FIELD_BYTES_0` and
cannot be intercepted.

**Cost.** One `unordered_map` lookup per table entry, no DB query, no allocation, no iteration over
the spell store. This matters: `PlayerbotMgr.cpp:208` routes every bot login through
`HandlePlayerLoginFromDB`, so `Reconcile` runs for every bot on the realm.

Rank 1 of each ability is *also* granted for free by the core, via `SkillLineAbility`
`AcquireMethod = 2` → `learnSkillRewardedSpells`, at creation and again from `Player::_LoadSkills`
on every login. mod-learn-spells will independently hand out ranks 2+ on level-up. All three paths
agree; whichever runs first wins and the others find `HasSpell` true. This module is the
authoritative one — it is the only one that also covers login.

## Config

Five keys, documented in `conf/mod_dk_lowlevel.conf.dist`. The repo's override copy is
`conf/modules/mod_dk_lowlevel.conf` and it must exist in the same commit as this module, because
`deploy/docker-compose.yml` bind-mounts `../conf/modules` **as a directory** and shadows the
image's `/opt/ac/etc/modules` entirely.

`DKLowLevel.Enable` defaults to `0` and gates everything, including the talent hook. At `0` the
module is indistinguishable from not being compiled in, which is what makes it safe to ship the
image before the SQL. `DKLowLevel.Enable` is read live on each call; the other four are cached in
`sDkLowLevelConfig` and refreshed from `OnAfterConfigLoad`, so `.reload config` applies all five
with no restart. `OnAfterConfigLoad` logs the resolved state to `server.loading` — that log line is
how you confirm a flip took.

The compiled-in defaults in `DkLowLevelConfig::Load` must stay identical to the `.conf.dist`
values. A key omitted from `conf/modules/mod_dk_lowlevel.conf` falls back to the compiled literal,
never to the `.dist`, because the `.dist` is not read at runtime at all.
