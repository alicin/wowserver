# mod-utility-npcs

Six utility NPCs were installed on this realm and nobody ever spawned them. Their
`creature_template` rows existed; their `creature` rows did not, so they were not in the world.
This module is the missing half: **734 spawns**, at every inn, at every starting zone, and at
fourteen places worth walking to.

Player-facing documentation — who they are, what they do, where to find them — is
`docs/utility-npcs.md`. This file is the mechanics.

## Layout

```
build/modules/mod-utility-npcs/
  conf/mod_utility_npcs.conf.dist    REQUIRED — see below
  src/utility_npcs.h                 hook declarations, config struct, generated-header asserts
  src/utility_npcs.cpp               the off switch and the boot-time guid audit
  src/utility_npcs_loader.cpp        Addmod_utility_npcsScripts()
  src/utility_npcs_range.h           GENERATED by tools/gen_spawns.py — DO NOT HAND-EDIT
  tools/npc_spec.py                  every human decision: guid block, rosters, ring, surprises
  tools/gen_spawns.py                the generator (SQL + the header), --check, --plan
  data/sql/db-world/base/*.sql       GENERATED; picked up by UpdateFetcher at boot
  .gitignore                         re-includes data/ — read it before deleting it
```

Same conventions as `mod-dk-lowlevel`, for the same reasons: no `CMakeLists.txt` (the core
enumerates `modules/*/src` and globs it), a required `conf/*.conf.dist` (a module without one
never gets its `.conf` read at all), and `data/` re-included by a local `.gitignore` because the
repo root ignores a bare `data/` at any depth.

No Dockerfile change was needed. `build/Dockerfile` already does `COPY modules/ /src/modules/`
after the clone loop, so a new directory here is picked up automatically, SQL and all.

## The module is 95% data

The SQL migration is the feature. It applies itself through `UpdateFetcher` at worldserver boot,
which is how the low-level Death Knight work deployed to a fresh VPS with no manual SQL step, and
it is how this deploys too. There is nothing to run by hand.

The C++ exists for the two things a `creature` row cannot do:

1. **The off switch.** There is no `enabled` column on a spawn.
2. **The boot-time guid audit.** The generator checks the reserved block against whatever
   database it was pointed at on the day someone ran it. The C++ checks it against the database
   this worldserver actually booted on, every boot — which is the check that survives a world-DB
   update or a restore from somebody else's dump.

## Placement

| kind | anchors | roster | spawns |
|---|---:|---:|---:|
| inns | 122 | 5 | 610 |
| starting zones | 8 | 5 | 40 |
| surprises | 14 | 6 | 84 |
| | | | **734** |

By map: 149 on Eastern Kingdoms, 169 on Kalimdor, 198 in Outland, 218 in Northrend. Inn rings per
map: 22 / 26 / 34 / 40.

### Is 734 a lot?

No, and the number was checked rather than assumed. It is **+0.49%** on a `creature` table that
already holds 149,975 rows (734 / 149,975), spread across four continent maps. The densest single
place is Dalaran, which has five rings — 25 creatures — over a city that already holds several
hundred. There is no measurable world-DB size or grid-load cost here.

The real cost of "every inn" is not rows, it is **clutter** — nameplates and click targets in a
cramped room — and that is what the roster and the ring geometry are tuned against. Two levers
exist if it ever feels like too much, both one line in `tools/npc_spec.py` followed by a re-run:

* shrink `ROSTER_INN`. Dropping to `(190010, 9000000)` — the transmogrifier and Gabriella, who
  between them cover most of what the other three do — takes inns from 610 spawns to 244 and the
  total to **368**, while starting zones and the surprises keep the full set.
* raise `MIN_ANCHOR_SEPARATION` from 30. At 100 yards Dalaran collapses from five rings to three.

Neither is applied today, because the request was every inn and 734 is not a load problem. They
are documented because "we could reduce it" is only true if somebody wrote down how.

**Not one coordinate was typed in.** Every position is an offset from a row that already exists
on the realm. That is the whole safety argument — a made-up x/y/z lands inside terrain, under the
water table or in the void, and the NPC is then unreachable or falls forever.

* **Inns** anchor on `creature JOIN creature_template WHERE npcflag & 65536`
  (`UNIT_NPC_FLAG_INNKEEPER`). There is no `inn` table and a hand-written list would go stale the
  first time a module adds one. An innkeeper's position is a free guarantee of *indoors, on valid
  ground, in a building with a door, facing into the room*. 124 exist; two Dalaran ones are
  thinned out because they stand within 30 yards of another (see `MIN_ANCHOR_SEPARATION`).
* **Starting zones** anchor on `playercreateinfo`, merged spatially. Ten races share eight
  distinct points — orc/troll both start in the Valley of Trials, dwarf/gnome both in Coldridge
  Valley — and the merge also folds the rounded duplicate the DK feature's `playercreateinfo`
  edit left behind (gnome classes 4/8/9 read `-6240, 331, 383`, classes 1/6 read
  `-6240.32, 331.033, 382.758`; the same patch of snow at two precisions).
* **Surprises** anchor on `game_tele`, by NAME. Those rows are curated, human-named and were
  captured by someone standing there. They were captured for a *player teleport*, though, which
  tolerates a short drop — so the generator additionally corroborates each one against the live
  `creature` and `gameobject` tables and refuses any anchor with no existing spawn at the same
  height nearby. Three otherwise excellent candidates were cut by that check; they are listed at
  the bottom of `tools/npc_spec.py` so nobody re-adds them.

### The ring

Radius 2.5 yd indoors, 4.0 yd outdoors, at ±30 / ±90 / ±150 degrees off the **anchor's own
facing**.

A ring rather than a line: a line has two ends that stick out, and in a room the size of the
Lion's Pride Inn one of those ends is in a wall. Rotating it 30° off the facing means nothing is
placed at 0° — the lane a player walks up to talk to the innkeeper, which has to stay clear so
their own click target is reachable — and nothing at 180°, which behind an innkeeper is the bar,
the hearth or the wall. The set fans outward from the front, so if the roster ever shrinks the
survivors keep the most open floor.

Adjacent spacing on a 60°-stepped ring is exactly the radius, so 2.5 yd indoors against a
worst-case bounding radius of 0.4213 (`creature_model_info`, display 31833) leaves about 1.6 yd of
clear air between neighbours. Z is **copied** from the anchor, never computed: the anchor's z is
the floor.

Each NPC faces the anchor. Facing outward would point the back half of the ring nose-first into
whatever the innkeeper has behind them; facing inward can only ever point at the anchor, which is
by definition standable floor.

### Why five at inns and not six

`190010 Warpweaver` and `190011 Ethereal Warpweaver` are not two NPCs. Same `ScriptName`
(`npc_transmogrifier`), same subname, same faction, and — the part that settles it — the same
`CreatureDisplayID` **19646** in `creature_template_model`. A player cannot tell them apart by
sight or by service. 122 identical pairs of twins is 122 wasted rows.

So the duplicate is not dropped, it is posted somewhere interesting: 190011 gets the fourteen
surprise locations, where a second transmogrifier reads as a joke instead of a bug. This is three
tuples in `npc_spec.py` (`ROSTER_INN`, `ROSTER_START`, `ROSTER_SURPRISE`); change them and re-run.

## The reserved guid block: 10,000,000 – 10,099,999

Four measured numbers, from the live realm:

```
MAX(guid) FROM creature ................  5,300,688
COUNT(*) WHERE guid >= 6,000,000 .......          0
COUNT(*) WHERE guid IN the block .......          0
the hard ceiling ....................... 16,777,215   = 0xFFFFFF
```

**The ceiling is not the column width.** `creature.guid` is `INT UNSIGNED`, but
`ObjectMgr::GenerateCreatureSpawnId` (`ObjectMgr.cpp:7655-7662`) calls `World::StopNow` — the
worldserver shuts itself down — as soon as the next spawn id would reach `0xFFFFFF`. The whole
usable space is 1..16,777,214, so the tempting "put it up at four billion, nothing will ever reach
it" is a realm that dies the first time a GM types `.npc add`.

10,000,000 sits at 60% of that space: 4.7M of untouched room below for the upstream world DB to
grow into (it would have to nearly double), 6.68M above for GM spawns, and 100,000 guids in the
block against 734 in use — 136× headroom.

**The guids count DOWN from the top of the block, and that is load-bearing.** `ObjectMgr` seeds
`_creatureSpawnId = MAX(guid) + 1` at boot (`ObjectMgr.cpp:7616-7618`), so this module's highest
row decides where `.npc add` starts handing out ids. Packing upward from 10,000,000 would put the
very next GM spawn *inside* the reserved range, where the next generator run would delete it
without asking. Packing downward pins `MAX(guid)` at exactly 10,099,999 for as long as this module
has a single spawn, so `.npc add` always begins one clear of the block. Generator invariant #3 is
the assertion that the top slot is occupied.

Encroachment is checked in two places: `tools/gen_spawns.py --check` (invariant #5, against
whichever DB you point it at) and `utility_npcs_worldscript::OnStartup` (three indexed queries at
every boot, against the DB the server is actually on).

## Idempotence

The migration is `DELETE` the **whole reserved range**, then `INSERT`. Not "delete the guids we
are about to insert" — the range — because a future run that emits fewer rows must leave nothing
behind.

`UpdateFetcher` keys a migration on its bare filename plus a SHA1 of its contents: an unchanged
file is skipped, a **changed** file is re-applied in full. A bare `INSERT` would therefore work
exactly once and fail on the second edit. Generator invariant #8 parses the emitted file back off
disk and checks that every `INSERT` guid falls inside a `DELETE` range in the same file.

`updates.name` is the primary key, so migration filenames must be unique across *all* modules, not
just this one. `2026_08_08_20_utility_npcs_spawns.sql` does not collide with the DK module's
`_00/_01/_02` or `mod-autolearn`'s `_00`.

## Schema notes for this exact revision

Read from `SHOW COLUMNS` and from the core, not from a wiki. Most of what is online is wrong for
this revision.

* `creature` has **`id`**, not `id1`. Alternate entries live in `creature_multispawn`.
* `creature_template` has **no `modelid1..4`**. Models are rows in `creature_template_model`.
* There is **no `faction` column on `creature`.** Faction is the template's, full stop — so
  "give them a friendly faction" is satisfied by *verifying* rather than by writing. Generator
  invariant #6 fails unless all six entries are faction **35**, which is `FACTION_FRIENDLY`
  (`src/server/shared/SharedDefines.h:189`), the same faction 5,002 other templates on this realm
  use including the Spirit Healer and seven of its own innkeepers.
* `npcflag` / `unit_flags` / `dynamicflags` on the spawn row are **0, meaning inherit**.
  `ObjectMgr::ChooseCreatureFlags` (`ObjectMgr.cpp:1659-1676`) starts from the template and
  overrides a field only when the spawn row's value is non-zero. Writing 0 is how each NPC keeps
  its own npcflag (1 `GOSSIP`, 129 `GOSSIP|VENDOR` for Gabriella) and unit_flags (2
  `UNIT_FLAG_NON_ATTACKABLE` on three of the six). Copying the template's values in would be
  equivalent today and would silently freeze them the day the owning module changed one.
* `ScriptName` on the spawn row is **empty, and must stay that way**. `LoadCreatures` does
  `if (!data.ScriptId) data.ScriptId = cInfo->ScriptID;` (`ObjectMgr.cpp:2394-2395`) — an empty
  spawn-row script means the *template's* script runs. Naming anything there would replace
  `npc_transmogrifier` / `npc_assistant` / `instance_reset` with nothing.
* `equipment_id` is **derived**, not constant: `MIN(ID)` from `creature_equip_template` for that
  entry, else 0. Exactly one of the six has a row — Beauregard Boneglitter ships equip ID 1, item
  11343 — and hardcoding 0 would strip the weapon his own module gave him.
* `curhealth` / `curmana` are derived from `creature_classlevelstats` the way
  `Creature::SelectLevel` computes them, and are **not read at all** while
  `creature_template.RegenHealth = 1`, which is true for all six today
  (`Creature.cpp:1753-1770` takes the `GetMaxHealth()` branch). They are filled in correctly
  anyway so that a future `RegenHealth = 0` yields a normal NPC and not a 1 hp one.
* `zoneId` / `areaId` are 0. `LoadCreatures` does not select them; they are a cache the server
  writes back only under `CONFIG_CALCULATE_CREATURE_ZONE_AREA_DATA`, and 144,975 of this realm's
  149,975 existing rows have `zoneId` 0.
* `MovementType` 0 and `wander_distance` 0 — and the second **must** be 0 while the first is, or
  the core logs an `sql.sql` error and zeroes it anyway (`ObjectMgr.cpp:2462-2470`).
* `Comment` carries provenance (`mod-utility-npcs [inn] 79841 Innkeeper Allison`). Nothing in the
  core reads it; a GM running `SELECT * FROM creature WHERE guid = …` does.

## The generator

```
tools/gen_spawns.py            emit the SQL and the header (needs a world DB, read-only)
tools/gen_spawns.py --plan     print the placement plan and the counts, write nothing
tools/gen_spawns.py --check    re-verify what is on disk, write nothing
tools/gen_spawns.py --mysql-cmd '<argv>'    point it at a different world DB
```

`Db.query` refuses anything that is not `SELECT` or `SHOW`. The tool never applies SQL and never
writes to the database; the worldserver does that, at boot, through `UpdateFetcher`.

Output is deterministic — anchors are ordered by guid, races by number, surprises by spec order —
so re-running against an unchanged database rewrites nothing. Thirteen numbered invariants are
hard failures in both `--emit` and `--check`; they are listed in the module docstring at the top
of `gen_spawns.py`. The interesting ones:

* **#1** the `creature` column list is exactly the live table's, in order. A wrong column count
  is an apply-time abort part-way through, not a warning.
* **#3** the top of the guid block is occupied (see above).
* **#5** nothing foreign is in the block, and the rest of the world DB has not grown into it.
* **#9** every surprise anchor is corroborated by an existing spawn at the same height.
* **#13** every emitted value fits its column's declared type. This realm runs
  `STRICT_TRANS_TABLES`, so an out-of-range value aborts the migration mid-file and leaves the
  realm with some of these NPCs and not others.

`src/utility_npcs_range.h` is emitted by the same run, from the same spec, so the range the C++
polices and the range the SQL deletes cannot drift. Invariant #12 diffs the two. The header is a
hard build dependency: the module will not compile without it.

## Config

One key, `UtilityNPCs.Enable`, documented in `conf/mod_utility_npcs.conf.dist` and repeated in the
repo's `conf/modules/mod_utility_npcs.conf` (which must exist in the same commit, because
`deploy/docker-compose.yml` bind-mounts `../conf/modules` **as a directory** and shadows the
image's `/opt/ac/etc/modules` entirely).

At 0 the module calls `Unit::SetVisible(false)` on every spawn in the reserved block as its grid
loads — invisible and unclickable to players, still visible to GMs. It does **not** delete rows.

**The flip is not instant.** `AllCreatureScript::OnCreatureAddWorld` runs once per creature per
*grid load*, so `.reload config` applies to each spawn the next time its grid loads, which for a
busy city inn may be never. A worldserver restart applies it everywhere. That is a deliberate
trade: the instant version means overriding `OnAllCreatureUpdate`, which costs a virtual dispatch
per creature per world tick forever, on a realm that runs playerbots. A config flip is a rare
operator act; paying for it continuously is the wrong side of that trade.

> **`AllCreatureScript::CanCreatureGossipHello` is a trap.** It is declared in
> `AllCreatureScript.h:67` and is **never dispatched** on this fork — the only caller of that name
> is `CreatureScript.cpp:31`, which belongs to the per-entry `CreatureScript` class. Overriding it
> here compiles perfectly and does nothing at all. `OnCreatureAddWorld` *is* dispatched, from
> `Creature::AddToWorld` (`Creature.cpp:333`), after `Unit::AddToWorld` has set `IsInWorld` —
> which is what makes `SetVisible`'s `UpdateObjectVisibility` legal there.

Hooks are opted into explicitly. `WorldScript`'s constructor treats an empty `enabledHooks` vector
as "every hook" (`WorldScript.cpp:87-96`), which would register this script against all thirteen
dispatch lists for the sake of two. And `WorldScript` kept its original method names — the
`OnPlayerXxx` renaming on this fork is `PlayerScript`-only.
