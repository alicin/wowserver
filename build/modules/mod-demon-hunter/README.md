# mod-demon-hunter

The Demon Hunter as a **real player class, class id 10** — the vacant `//CLASS_UNK = 10` slot
between Warlock and Druid. `tools/dh_spec.py` is the source of truth for the class; this file
covers only the C++ module.

The module is a small part of the feature. Almost all of it is data: world-DB `*_dbc` override
rows, `playercreateinfo*` rows, three talent trees and a client patch MPQ, all emitted by
`tools/dhspells.py` from `tools/dh_spec.py` in one run. Plus eight lines of core patch
(`build/patches/0001-demon-hunter-class-10.patch`) for the six per-class float tables that are
indexed `getClass() - 1` directly and so cannot be reached from any hook.

The module exists to do the four things neither data nor the patch can do:

| # | what | why it cannot be data |
|---|---|---|
| 1 | hand out the ability ladder the character has grown into | there is no trainer for class 10 and no other module knows about family 16 |
| 2 | answer, per `ClassContext`, **which existing class a Demon Hunter is** | the entire point of `Player::IsClass`; there is no table for it |
| 3 | grant `674` Dual Wield, `3127` Parry and one racial per elf race | their stock `SkillLineAbility` `ClassMask`s predate class 10 |
| 4 | refuse Double Jump / Glide when the caster is not falling | `Spell.dbc` has no "requires falling" cell |

`CLASS_DEMON_HUNTER` **does not exist in `.work/ac-src`.** It is added by the core patch, which
`build/Dockerfile` applies to `/src` after the module `COPY` and before the compile. The checkout
on disk still reads `//CLASS_UNK = 10` at `SharedDefines.h:135`; that is expected, and the
reference in `demon_hunter.cpp` is not broken.

## 1. Layout

```
build/modules/mod-demon-hunter/
  conf/mod_demon_hunter.conf.dist   REQUIRED — see below
  src/demon_hunter.h                hook declarations, config struct, generated-table asserts
  src/demon_hunter.cpp              Reconcile(), the IsClass table, the movement gate
  src/demon_hunter_loader.cpp       Addmod_demon_hunterScripts()
  src/dh_progression.h              GENERATED by tools/dhspells.py — DO NOT HAND-EDIT
  tools/dh_spec.py                  THE source of truth for the class
  tools/dhspells.py                 the one generator (SQL + client DBC + the header)
  data/sql/db-world/base/*.sql      generated migrations, picked up by UpdateFetcher
  client/*.patch                    the GlueXML/FrameXML patches
```

**There is no `CMakeLists.txt`, and adding one would do nothing.** The core's
`modules/CMakeLists.txt` never calls `add_subdirectory` on a module; it enumerates `modules/*`
that contain a `src/` directory and globs that `src/` with `CollectSourceFiles`.
`CollectIncludeDirectories` on the same path is what puts `src/` on the include path, which is how
`#include "dh_progression.h"` resolves.

`conf/mod_demon_hunter.conf.dist` **is** required, and its absence fails silently: the compile-time
`CONFIG_FILE_LIST` is built from `file(GLOB ${MODULE_CONFIG_PATH}/*.conf.dist)`, and a module with
no `.conf.dist` never has its `.conf` opened at all.

**Do not add this module to `build/modules.txt`.** That file is a list of GitHub pins — the
Dockerfile reads it as `while read -r repo ref sha` and runs
`git clone https://github.com/$repo.git`. A one-field line would break the read loop. Local
modules reach the image through `COPY modules/ /src/modules/`, which sits immediately after the
clone loop precisely so that a name collision resolves in favour of the tree in this repo.
`mod-dk-lowlevel` is not in `modules.txt` either.

## 2. The generated header is a hard build dependency

`src/dh_progression.h` is emitted by `tools/dhspells.py`. The module will not compile without it,
so the generator has to have been run at least once — for the header alone if nothing else —
before the first image build. The contract `demon_hunter.h` compiles against:

```cpp
struct DhGrant
{
    uint8  level;
    uint32 spellId;
};

constexpr DhGrant kDhProgression[] =
{
    { 1, 91000 },        // ascending by level then spell id, no zero levels, no zero spell IDs
};
```

`demon_hunter.h` `static_assert`s that the table is non-empty, sorted, and free of zero levels and
spell IDs. Sortedness is not cosmetic — `Reconcile` early-outs with `break` on the first entry
above the player's level, so an unsorted table hands out a partial spellbook that looks entirely
plausible in game.

**`DhGrant` / `kDhProgression`, never `DkGrant` / `kDkProgression`.** `mod-dk-lowlevel` is linked
into the same `worldserver` binary and defines a struct of that name. Two statically-linked
modules defining different structs under one name is an ODR violation: it links silently and
misbehaves at runtime. The distinct names are the whole guard.

## 3. The hooks

Opted into explicitly. `PlayerScript`'s constructor treats an empty `enabledHooks` vector as "all
hooks" (`PlayerScript.cpp:963-971`), which would register the script against all **192** dispatch
lists (`PlayerScript.h:30-224`) for the sake of three.

| hook | fork signature | why this one |
|---|---|---|
| `PLAYERHOOK_ON_LOGIN` | `void OnPlayerLogin(Player*)` — `PlayerScript.h:337` | Fires at `CharacterHandler.cpp:1131`, inside `HandlePlayerLoginFromDB` (`:802`), after `AddPlayerToMap` and after `m_playerLoading = false`, so `learnSpell`'s `if (IsInWorld()) SendLearnPacket(...)` (`Player.cpp:3427-3428`) reaches the client. Fires *before* `OnPlayerFirstLogin` (`:1136`), so first login needs no separate hook. It is the only thing that catches an **offline** `.character level`, which writes raw `CHAR_UPD_LEVEL` SQL with no hook at all (`cs_character.cpp:271-276`). |
| `PLAYERHOOK_ON_LEVEL_CHANGED` | `void OnPlayerLevelChanged(Player*, uint8)` — `PlayerScript.h:267` | Fires at `Player.cpp:2583`, after `SetLevel` at `:2521`, so `GetLevel()` is already the new level and the argument is the old one. |
| `PLAYERHOOK_ON_PLAYER_IS_CLASS` | `Optional<bool> OnPlayerIsClass(Player const*, Classes, ClassContext)` — `PlayerScript.h:526` | The centrepiece. See below. |
| `ALLSPELLHOOK_ON_SPELL_CHECK_CAST` | `void OnSpellCheckCast(Spell*, bool, SpellCastResult&)` — `AllSpellScript.h:57` | The Double Jump / Glide falling gate. Dispatched from the first lines of `Spell::CheckCast`. |
| `WORLDHOOK_ON_AFTER_CONFIG_LOAD` | `void OnAfterConfigLoad(bool)` — `WorldScript.h:53` | Refreshes the three cached knobs on `.reload config` (`World.cpp:301`), logs the resolved state, and checks the two movement spell IDs against `kDhProgression`. |

> **Every `PlayerScript` virtual on this fork is `OnPlayerXxx`.** `OnLogin` and `OnLevelChanged`
> — the names in every AzerothCore tutorial — do not exist here. Writing one compiles perfectly:
> you have declared a new non-virtual member and the hook never fires. `override` on all of them
> is the guard, and it is the reason the table cites line numbers. The renaming is
> `PlayerScript`-only; `WorldScript::OnAfterConfigLoad(bool)` (`WorldScript.h:53`) kept its name.

**Why `AllSpellScript` and not `SpellScript`.** A `SpellScript` is bound to its spell through the
world table `spell_script_names` (`ObjectMgr.cpp:6345`), so using one would mean this module
shipping SQL — and `tools/dh_spec.py` owns every SQL statement in this feature.
`AllSpellScript::IsDatabaseBound()` is `false` (`AllSpellScript.h:52`): it is registered in code,
needs no row, and leaves the generator's ownership of data intact.

## 4. `OnPlayerIsClass` — the centrepiece

`Player::IsClass` (`Player.cpp:1348-1355`) asks this hook *before* comparing `getClass()`:

```cpp
Optional<bool> scriptResult = sScriptMgr->OnPlayerIsClass(this, unitClass, context);
if (scriptResult != std::nullopt)
    return *scriptResult;
else
    return (getClass() == unitClass);
```

That is why an eleventh class is viable without a core-wide audit. **149 `IsClass(CLASS_…` call
sites across 26 files** funnel through it (measured:
`grep -rno "IsClass(CLASS_[A-Z_]*" --include='*.cpp' --include='*.h' src/`), each carrying a
`ClassContext` (`UnitDefines.h:231-251`) that says *why* it is asking.

`std::nullopt` is not a shrug. It means "use your own comparison", which for a Demon Hunter is
false against every existing class — i.e. it is the positive answer *"a Demon Hunter is a Demon
Hunter here"*, and it is right far more often than not. Each row below was decided by reading the
call sites, not the enum.

**Cost.** Every `IsClass` call on the realm enters this function, because
`ScriptMgr::OnPlayerIsClass` (`PlayerScript.cpp:576-588`) only short-circuits when the hook list is
empty and ours is not. The `getClass()` test is therefore first and load-bearing: one
`UNIT_FIELD_BYTES_0` read and a compare rejects every non-Demon-Hunter before the config lookup
below it, which costs a string hash and which only a real Demon Hunter ever pays.

## 5. `Reconcile`

```
if not DemonHunter.Enable      -> return
if player->getClass() != 10    -> return
for each { level, spellId } in kDhProgression, ascending:
      if level > player level  -> break
      if not HasSpell(spellId) -> learnSpell(spellId)
then the three untrainables, each behind its knob and a HasSpell guard:
      674 Dual Wield, 3127 Parry, and the race's own class-gated racial
```

**Idempotent.** The only mutation is `learnSpell` behind `HasSpell`. `HasSpell` (`Player.cpp:4039`)
is true for a known-but-inactive spell, which is what we want: a rank superseded by a higher one
is still owned. `learnSpell` early-returns on `HasActiveSpell` (`Player.cpp:3412-3417`) anyway, so
the guard is for cost — one `unordered_map` lookup per entry, no allocation, no log line — which
matters because `mod-playerbots` routes every bot login through
`WorldSession::HandlePlayerLoginFromDB` and therefore through `OnPlayerLogin`.

**Correct in both directions.** Levelling up, online or offline, converges on the next hook or the
next login. Levelling down is a no-op: this function never revokes. `Player::removeSpell`
(`Player.cpp:3492`) removes higher ranks *recursively*, so a revoke pass would turn a GM typo into
a destroyed spellbook.

**`getClass()`, never `IsClass()`** — and here the reason is sharper than it was for the Death
Knight. `Player::IsClass` consults `OnPlayerIsClass`, and in this module's case the module
answering *is this file*: `IsClass(CLASS_DEMON_HUNTER, CLASS_CONTEXT_STATS)` returns **false** on a
Demon Hunter, because the honest answer to that context is `CLASS_ROGUE`.

**Unlike the Death Knight, there is no second path.** `mod-dk-lowlevel` can note that rank 1 of its
level-1 abilities also arrives via `SkillLineAbility AcquireMethod = 2`, and that `mod-learn-spells`
independently hands out ranks 2+. Neither is true here (see §8). This loop is the only thing on the
realm that gives a Demon Hunter a Demon Hunter spell.

## 6. The three untrainable spells

A Demon Hunter has **no class trainer**, and every stock `SkillLineAbility` row was authored when
class 10 did not exist, so no `ClassMask` can contain bit `512`. Both halves of the normal
acquisition path are shut. Three spells fall through the gap, and each was found by reading the
stock `SkillLineAbility.dbc` row and the live `acore_world` tables.

### `674` Dual Wield — `DemonHunter.DualWieldLevel`

Its only row is `(SkillLine 118, ClassMask 109, RaceMask 0, AcquireMethod 2)`. `109` is
warrior|hunter|rogue|death knight|shaman. `Player::learnSkillRewardedSpells` skips any row whose
`ClassMask` misses the player (`Player.cpp:12270-12274`), so the `skill 118` row that
`dh_spec.py` puts in `playercreateinfo_skills` gives the Demon Hunter the **skill** and not the
**spell**.

`SPELL_EFFECT_DUAL_WIELD` (`SpellEffects.cpp:2700-2705`) is the only thing in the core that sets
`CanDualWield` for a player, and without it `Player::FindEquipSlot` never offers
`EQUIPMENT_SLOT_OFFHAND` (`PlayerStorage.cpp:186-187`). **A dual-wielding class that cannot equip
an off-hand is not a partial feature, it is the wrong class.**

674 is passive (`Attributes 0x50`), so `learnSpell` is sufficient: `Player::addSpell` casts a learnt
passive at `Player.cpp:3317-3321`, and `_LoadSpells` re-runs `addSpell` on every login. It must
also be *owned* and not merely applied, because `Player::resetTalents` (`:3938-3939`) and
`Player::ActivateSpec` (`:15663-15664`) both revoke `CanDualWield` from anyone who does not
`HasSpell(674)`.

### `3127` Parry — `DemonHunter.ParryLevel`

Two rows, neither reachable: `(95 Defense, ClassMask 15, AcquireMethod 0)` — trainer-taught, and
the live `acore_world.npc_trainer` has exactly four rows for it (IDs 200001/200004/200014/200016,
`ReqLevel` 6/8/8/12), all on class trainers; and `(95 Defense, ClassMask 32, AcquireMethod 1)` —
the Death Knight's automatic grant.

`Player::SetCanParry` is reached from exactly two places: `SPELL_AURA_MOD_PARRY_PERCENT`
(`SpellAuraEffects.cpp:4606`) and `SPELL_EFFECT_PARRY` (`SpellEffects.cpp:4690-4697`), which is
3127's `Effect_1`. `Player::UpdateParryPercentage` opens with
`if (CanParry() && parry_cap[pclass] > 0.0f)` (`StatSystem.cpp:774`) — **both** halves are
required, so without the spell the `parry_cap[9] = 145.560408f` that `build/patches/0001` adds
*specifically because a Demon Hunter parries* is dead code. The character sheet would read 0%
and be telling the truth.

### One racial per race — `DemonHunter.GrantRacials`

Most elf racials carry `ClassMask 0` and arrive untouched: a Night Elf gets `20583` Nature
Resistance, `20582` Quickness, `20585` Wisp Spirit and `58984` Shadowmeld; a Blood Elf gets `822`
Magic Resistance and `28877` Arcane Affinity. Exactly one row per race is class-gated:

* **`21009` Elusiveness** — `(126, ClassMask 1085, RaceMask 0x8, AcquireMethod 2)`; `1085` is
  warrior|hunter|rogue|death knight|shaman|druid. "Reduces the chance enemies have to detect you
  while Shadowmelded or Stealthed" — and the Demon Hunter *has* Shadowmeld.
* **`25046` Arcane Torrent, the ENERGY variant** — `(756, ClassMask 8, …)`. `8` is Rogue alone,
  because in 3.3.5a the Rogue was the only Blood Elf class on energy. The other two rows on skill
  756 are `28730` (`ClassMask 406`, the mana classes) and `50613` (`ClassMask 32`, runic power).
  `dh_spec.py CREATE_ACTION_RACE_SPELL` already puts 25046 on button 2 of a Blood Elf's starting
  bar, so without this grant that button is blank at character creation — which is also why this
  knob is a bool and not a level.

**Why grant from the module rather than widen the stock `ClassMask` in `skilllineability_dbc`.**
Both work. The module is chosen because widening a stock row edits a record every other class
reads, while a `learnSpell` behind a `HasSpell` guard touches nothing but this character. If the
data half ever takes them over, these calls become no-ops the first time `HasSpell` answers true.

## 7. Double Jump and Glide

**The protocol is a spell cast, not an addon message.**
`.work/dh-parts/addon/DemonHunter/Movement.lua:280-285` writes the numeric spell id into a `SecureActionButtonTemplate`'s `spell`
attribute, so the *client* casts through its own `SECURE_ACTIONS.spell` → `CastSpellByID` path and
what arrives is an ordinary `CMSG_CAST_SPELL`. There is nothing to parse and no channel to wire up.

*(For the record, had there been one: this fork has no `OnPlayerChat` at all. Addon traffic
surfaces as the five `PlayerScript::OnPlayerCanUseChat` overloads — `PlayerScript.h:659`, `:672`,
`:685`, `:698`, `:711` — keyed on `language == LANG_ADDON`, dispatched from
`ChatHandler.cpp:469-656`; `CHAT_MSG_ADDON` only ever rides on PARTY/RAID/GUILD/BATTLEGROUND/WHISPER,
`ChatHandler.cpp:186-195`.)*

So the only server half is `NOTES.md` §5.4:

> A cast of either spell while the caster is not falling must fail silently and cost no global
> cooldown (`SPELL_FAILED_DONT_REPORT`).

That is not a nicety, and `NOTES.md` §2.4 proves it: the addon *physically cannot* make this
decision during combat — `IsFalling` is not in the restricted environment, there is no `falling`
macro conditional in the client binary, and insecure code cannot hand the value into a secure
snippet under lockdown. The glide key therefore stays bound at all times and a grounded press
really does reach the server. If the server does not reject it, nobody does.

**It fails for free.** The hook is dispatched from the first lines of `Spell::CheckCast`
(`Spell.cpp:5664-5669`); `Spell::prepare` calls `CheckCast` at `:3522` and only reaches
`TriggerGlobalCooldown` at `:3686`, so a failure written into `res` returns out of `prepare` at
`:3538-3541` before the GCD, before the power cost and before any cooldown is set.
`SPELL_FAILED_DONT_REPORT` sends no packet.

**`Unit::IsFalling`, never `Player::IsFalling`.** Neither is virtual and the `Player` one *hides*
the `Unit` one, so which runs is decided by the static type of the pointer.

| | what it reads | |
|---|---|---|
| `Unit::IsFalling` (`Unit.h:1718`, `Unit.cpp:15933`) | `MOVEMENTFLAG_FALLING \| MOVEMENTFLAG_FALLING_FAR` plus a falling spline | the same fact the addon's `IsFalling()` reads — **correct** |
| `Player::IsFalling` (`Player.h:1137`, `Player.cpp:2189`) | `GetPositionZ() < m_lastFallZ && !IsInFlight()` | false for the whole *rising* half of a jump, i.e. it would reject the double jump at the apex |

### Anti-cheat

`AnticheatHandleDoubleJump` (`PlayerScript.h:770`) is **not on this path**. It is consulted from
exactly one place, `WorldSession::VerifyMovementInfo` at `MovementHandler.cpp:567`, and only when
`opcode == MSG_MOVE_JUMP` — a *client-initiated* jump. Our jump is a server-sent
`SMSG_MOVE_KNOCK_BACK` from `SPELL_EFFECT_LEAP_BACK` (`Unit::JumpTo`, `Unit.cpp:15495`) answered by
`CMSG_MOVE_KNOCK_BACK_ACK`. Nothing changes if it were: the default is `return true` (allow), and
no module on this realm overrides it — verified by grepping a local checkout of the installed
module set (`mod-playerbots`, `mod-autobalance`, `mod-learn-spells`, `mod-transmog`, `mod-solo-lfg`,
`mod-aoe-loot`, `mod-ah-bot`, `mod-multibot-bridge`) for `AnticheatHandleDoubleJump`: **zero hits**.
None of the remaining ten pins in `modules.txt` is an anti-cheat or movement module, and
`azerothcore/mod-anticheat` — the module these hooks exist for — is not pinned at all.

### REQUIREMENT ON THE DATA HALF: Double Jump needs a cooldown

The module deliberately does **not** rate-limit the double jump, and this is the one place where
that is a live risk rather than a design note.

* the addon holds the jump key down and sends **repeated** casts on purpose — "the server's
  cooldown is the authority" (`NOTES.md` §7);
* `Spell::EffectLeapBack` (`SpellEffects.cpp:5056-5077`) applies a fresh upward impulse every time
  it lands, with no ground check and no state;
* `dh_spec.py`'s `Ability` for `double_jump` leaves `cooldown_ms` at its `0` default, and
  `docs/demon-hunters.md` §4 records Double Jump's cooldown as `—`, so this is a design
  decision to revisit rather than a generator oversight.

Together those are an **infinite levitation exploit**: mash the key and rise. `RecoveryTime` is a
`Spell.dbc` cell and therefore the generator's business — this module owns the falling gate because
there is no cell that can express it, and does not own the cooldown because there is one and using
it would be a second source of truth. Give `double_jump` a `cooldown_ms` (≈1500 is one jump arc).

A stricter rule — *once per airborne period*, which is what a double jump actually is — would need
a landing signal, i.e. a `MovementHandlerScript` (`MovementHook::MOVEMENTHOOK_ON_PLAYER_MOVE`,
dispatched at `MovementHandler.cpp:660`) firing on every movement packet from every player and bot,
plus per-player state. That is a real cost for a small gameplay difference, and it is not paid
here; a cooldown of roughly one jump arc is close enough and free.

While you are in that record: donor `74608` Jump Jets carries `StartRecoveryTime 1000` /
`StartRecoveryCategory 133` (read from `Spell.dbc`). `SINGLES_ORDER` describes Double Jump as
"pure vertical impulse, **no GCD**", so those two cells have to be zeroed in the clone or a
movement key eats a global cooldown. `12438` Slow Fall, the Glide donor, is already `0`/`0`.

## 8. `mod-learn-spells` hands a Demon Hunter 245 spells it should not have

**This module cannot fix it and does not try. Read this before creating the first Demon Hunter.**

`mod-learn-spells` (pinned at `016b92d5`, `LearnSpells.Enable = 1`, `LearnSpells.OnFirstLogin = 1`)
resolves a player's spell family from a `switch (p->getClass())` with no case for class 10, so a
Demon Hunter falls to `default: return SPELLFAMILY_GENERIC;` (`mod_learnspells.cpp:491-518`). It
then walks the entire spell store on every level-up and learns every spell that is
`SpellFamilyName == 0`, has `BaseLevel == level`, and has a `SkillLineAbility` row with
`RaceMask == 0 && AcquireMethod == 0` — **with no class-mask check at all**
(`mod_learnspells.cpp:415-465`).

Measured against `/srv/wow/data/dbc/Spell.dbc` (49,839 records) and `SkillLineAbility.dbc`, after
applying the module's own ignore list and its `POWER_FOCUS` filter: **245 spells across 21 levels**,
of which **15 arrive at level 1** —

```
3127 Parry            6560 LeCraft Test Spell   16268 Spirit Weapons
21156 Battle Stance Passive                     30153/30195/30197/47995 Intercept
34919 Vampiric Touch  35912 Master Buff (Magic) 38734 Master Ranged Buff
52175 Decipher        54968 Glyph of Holy Light 55533 Glyph of Healing Wave
66922 Flash of Light
```

— plus 59 Enchanting recipes at level 35 (all `SkillLine 333`), 38 Alchemy recipes at level 45,
and 79 more at level 60 of which 70 are Enchanting. Most of the bulk is therefore profession
recipes handed out for free to a character with no profession. Class 10 is the **first**
class ever to reach that `default:` branch; all ten stock classes map to a real family, which is
why nobody has hit this.

**None of the obvious fixes work.**

* *A hook.* `OnPlayerLearnSpell` (`PlayerScript.h:308`) is a `void` notification fired *after* the
  fact at `Player.cpp:3424`. It cannot veto.
* *`disables`.* `DisableMgr::IsDisabledFor(DISABLE_TYPE_SPELL, …)` *is* checked in that loop, but
  spell disables have no class mask — the flags are `PLAYER`/`CREATURE`/`PET`/`DEPRECATED`/`MAP`/
  `AREA`/`LOS` (`DisableMgr.h:44-53`). Disabling Parry or Flash of Light for class 10 means
  disabling them for everyone.
* *A reaper in this module.* Reconstructing the predicate and un-learning the matches would delete
  legitimately trained Enchanting recipes, and would be exactly as stable as another module's pin.

**The fix that does work is one line, in `mod-learn-spells`:**

```cpp
case CLASS_DEMON_HUNTER:
    return 14;      // no stock spell carries family 14 -> the scan matches nothing
```

Family **14** and not 16. Histogramming `SpellClassSet` over all 49,839 stock records gives
`{0: 40256, 1: 137, 3: 1200, 4: 736, 5: 1004, 6: 978, 7: 979, 8: 628, 9: 1151, 10: 740, 11: 1049,
12: 2, 13: 375, 15: 576, 17: 28}` — 14 and 16 both have **zero** members, confirming `dh_spec.py`'s
`SpellClassSet` analysis. Returning 16 (the Demon Hunter's actual family) would make
`mod-learn-spells` start granting Demon Hunter abilities by `BaseLevel`, including the second
records — the off-hand mirrors and impact spells nobody is meant to learn. Returning 14 makes the
scan match nothing at all and `ApplyAdditionalSpells` find no key.

Mechanically that belongs in `build/patches/` as a second patch: `git apply` runs from `/src` and
the module clones live at `/src/modules/…`, so a patch touching
`modules/mod-learn-spells/src/mod_learnspells.cpp` applies fine in the existing step. It is a
judgement call about a directory whose README says "last resort" — hence it is written up here and
not done. **It is not this module's bug, it is not gated by `DemonHunter.Enable`, and it starts the
moment a class-10 character exists.**

*Silver lining worth knowing:* `3127 Parry` is in that level-1 set, so until the fix lands, a
Demon Hunter gets Parry twice over — once from §6 and once by accident.

## 9. Other findings, and what the module deliberately does not do

**Metamorphosis needs no `SpellScript`, but form 23 logs an error.** `HandleAuraModShapeshift`
(`SpellAuraEffects.cpp:1986-2041`) switches on the form to pick a power type; the `case` list runs
`… FORM_ZOMBIE (0x15), FORM_METAMORPHOSIS (0x16), FORM_UNDEAD (0x19) …` and **skips 0x17**, so form
23 falls to `default:` and emits `LOG_ERROR("spells.aura.effect", "Auras: Unknown Shapeshift Type:
23")` on both apply and remove — two `ERROR` lines per cast. It is **cosmetic**: `PowerType` stays
`POWER_MANA`, so the `if (PowerType != POWER_MANA)` block is skipped and the Demon Hunter keeps
Fury, which is exactly what we want. `Player::InitDataForForm` (`Player.cpp:10765-10788`) likewise
falls to `default:` and re-reads the power type from `ChrClasses` — `DisplayPower 3`, energy.
Silencing the log would take two lines in the core patch (a `FORM_DEMON_HUNTER = 0x17` enumerator
and a `case`); that is a judgement call about log noise, not a defect, so it is not done here.

**But the form's DBC flags are load-bearing.** `SpellInfo::CheckShapeshift`
(`SpellInfo.cpp:1444-1497`) reads `SpellShapeshiftFormEntry::flags1`: `SHAPESHIFT_FLAG_STANCE`
(`0x1`) decides whether the form "acts as shifted", and
`SHAPESHIFT_FLAG_CAN_ONLY_CAST_SHAPESHIFT_SPELLS` (`0x400`, `UnitDefines.h:117` — its comment
says `NYI` and the comment is wrong, `SpellInfo.cpp:1490` reads it) **silences everything whose
`Stances` mask does not include the form**. `dh_spec.py` records that stock row 22 (the
warlock's) carries `0xd8`. Row 23 must not acquire that last flag, or a Demon Hunter in demon
form can cast nothing at all.

**`dh_spec.py`'s `SINGLES_ORDER` comments are stale, and it matters.** They say
`# 91300  double_jump` / `# 91301  glide`. `ABILITY_BLOCKS` says `"singles": 25, # 91500-91519`,
and `single_spell_id()` computes `91000 + 20*25 + index` = **91500 / 91501**. The code is right and
the comments predate the block moving from index 15 to 25. `NOTES.md` §5.2 asks for these two
numbers to be pasted into the marked `PLACEHOLDER` lines at the top of `Movement.lua`; pasting
91300 produces a keybind that casts a spell nobody owns, silently. `demon_hunter.cpp` derives them
from the same arithmetic and `static_assert`s the result, and `OnAfterConfigLoad` logs an error at
boot if either id is missing from `kDhProgression`.

**OPEN: nothing currently supplies Glide's forward impulse.** `docs/demon-hunters.md` §1.1
describes Glide as "feather-fall **plus a forward impulse**, cancelled on landing by
`AuraInterruptFlags`". The donor is `12438` Slow Fall, which is a single `FEATHER_FALL` effect, and
`dh_spec.py`'s note for `glide` mentions the feather fall and the landing cancel and nothing else.
So the impulse is promised by the design and delivered by neither half today. Two places it could
come from:

* **the record** — a second effect on the clone. Cheap, no state, and it is where every other
  number in this class lives. This is the recommended route.
* **this module** — `Unit::KnockbackFrom` (`Unit.h:1733`) in an `AfterCast`. Note what it does:
  `Unit::JumpTo` (`Unit.cpp:15495-15516`) builds `SMSG_MOVE_KNOCK_BACK` from scratch with `vcos`,
  `vsin`, `speedXY` and `-speedZ`, so it **replaces** the player's velocity rather than adding to
  it — it would cancel the fall they are already in and start a fresh arc. That may well look
  right next to a feather fall, but the magnitude would be a guess and it is not shipped as one.

It is deliberately not implemented here. *(UNVERIFIED on this client: whether a feather-falling
3.3.5a player keeps enough directional control that no impulse is needed at all. That is the
cheapest thing to check first, alongside `NOTES.md` §6 step 8.)*

**Not implemented, on purpose:** any hook that revokes; any per-player state; any SQL. The module
ships no migrations at all — `data/sql/db-world/base/` belongs entirely to `tools/dhspells.py`.

## 10. Config

Four keys, documented in `conf/mod_demon_hunter.conf.dist`. The repo's override copy is
`conf/modules/mod_demon_hunter.conf` and it must exist in the same commit as this module, because
`deploy/docker-compose.yml` bind-mounts `../conf/modules` **as a directory** and shadows the
image's `/opt/ac/etc/modules` entirely — so a key omitted from the override falls back to the
literal compiled into `demon_hunter.cpp`, never to the `.dist`.

| key | default | shipped | notes |
|---|---|---|---|
| `DemonHunter.Enable` | `0` | `0` | Master switch. Read **live** on every call, not cached. |
| `DemonHunter.DualWieldLevel` | `1` | `1` | `0` = never grant. |
| `DemonHunter.ParryLevel` | `1` | `1` | `0` = never grant. |
| `DemonHunter.GrantRacials` | `1` | `1` | |

At `Enable = 0` the module is **indistinguishable from not being compiled in**: no grants, no
`IsClass` opinions (every context returns `std::nullopt`, which is what the core does with no
module at all), and no falling gate. That is what makes it safe to ship the image long before the
SQL, the DBCs, the patched `Wow.exe` and the addon are ready — which is exactly where this feature
is today. The other three keys are cached in `sDemonHunterConfig` and refreshed from
`OnAfterConfigLoad`, so `.reload config` applies all four with no restart, and the module logs its
resolved state plus the size of `kDhProgression` (22 grants as generated today) to `server.loading` — that line is how you confirm
a flip took.

**The ordering gate is stricter than the Death Knight's.** Flipping `Enable` to 1 does not only
start granting spells; it switches the class's attack power, armour-class rolls and weapon-swap
lockout over to the Rogue answer in one step. With no `player_class_stats` rows for class 10 behind
that, a Demon Hunter is a Rogue-shaped hole. Apply the SQL, restart, verify a level-1 Demon Hunter
can be created and shows non-zero attack power, *then* flip it.
